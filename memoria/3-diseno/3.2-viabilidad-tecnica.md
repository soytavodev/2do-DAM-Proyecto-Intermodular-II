# 3.2. Estudio de viabilidad técnica

En este apartado reviso si puedo hacer Freenglish con lo que sé, con las herramientas que tengo y en el tiempo disponible. También explico por qué elegí cada tecnología y qué riesgos técnicos veo.


ELECCIÓN DE LA TECNOLOGÍA

App de Android y versión web: Kotlin Multiplatform con Compose Multiplatform.

En el módulo de Programación multimedia y dispositivos móviles trabajamos con Kotlin y Jetpack Compose en Android Studio, y la profesora pidió que la app funcione en Android y en web. Compose Multiplatform, de JetBrains, usa la misma forma de hacer pantallas que Jetpack Compose y permite compartir la mayor parte del código entre Android y el navegador. Así aprovecho lo que veo en clase y no tengo que hacer dos aplicaciones distintas.

Según la documentación oficial de Kotlin, Compose Multiplatform es estable en Android, y en la web (con Kotlin/Wasm) está en fase Beta. Beta quiere decir que funciona, pero que todavía puede tener cambios. Necesita navegadores actuales: Chrome 119 o superior, Firefox 120 o superior y Safari 18.2 o superior. Lo tengo en cuenta como riesgo y por eso hago primero la versión de Android.

Las alternativas que descarté fueron hacer la web aparte con otra tecnología (sería el doble de trabajo) y usar una tecnología web empaquetada como app (por ejemplo, React con Capacitor), porque no aprovecharía lo que vemos en el módulo.

Servidor: PHP con MySQL (MariaDB).

Es lo que usamos en Acceso a datos y en Programación de servicios y procesos, y ya tengo experiencia con PHP y MySQL de primero. La API es pequeña, así que no necesito un framework: la hago con PHP y PDO, que permite usar consultas preparadas para evitar inyecciones SQL.

Alojamiento del servidor: alwaysdata, plan gratuito.

Comparé varias opciones gratuitas. InfinityFree, que es muy conocido, lo descarté porque en el plan gratuito tiene un sistema de seguridad obligatorio que exige JavaScript y cookies, y eso bloquea las peticiones de una app a la API. Según sus propios foros, no se puede desactivar. Elegí alwaysdata porque su plan Free es gratis de por vida, sin publicidad, y según su web incluye 1 GB de disco SSD, 256 MB de memoria y un cuarto de CPU, con 3 días de copias de seguridad. Según su documentación admite PHP y bases de datos MariaDB (MySQL). Además es una empresa europea, lo que facilita cumplir el RGPD. El plan está pensado para uso personal, y para el volumen de un proyecto de clase es suficiente.

Envío de correos: Brevo, plan gratuito.

Para enviar los códigos de acceso uso Brevo, que tiene un plan gratuito de 300 correos al día con acceso por SMTP y por API. Para el número de usuarios que espero durante el proyecto alcanza de sobra.

Voz: la del propio dispositivo.

En Android uso el motor de texto a voz del sistema (TextToSpeech), y en la web, la síntesis de voz del navegador (Web Speech API). No hace falta grabar ni guardar audios.

Imágenes y contenido: archivos de datos.

El contenido va en archivos JSON dentro de la app, y las imágenes son propias o de colecciones con licencias libres compatibles (apartado 2.7).


COMPLEJIDAD TÉCNICA

La parte más compleja no es ninguna pantalla en particular, sino que todo funcione junto:

- la lógica del curso (corrección, avance por dominio, repetición espaciada);
- guardar el progreso en el dispositivo y sincronizarlo con el servidor sin perder datos;
- el inicio de sesión con código por correo y la seguridad de la API;
- compartir el código entre Android y web.

Lo demás (pantallas, lectura de archivos JSON, consultas a la base de datos) es del tipo de cosas que ya practicamos en clase.


CONOCIMIENTOS

Lo que ya sé: Kotlin básico, Jetpack Compose y la arquitectura por capas de clase; PHP y MySQL; HTML, CSS y JavaScript; Git y GitHub.

Lo que tengo que aprender: Kotlin Multiplatform y Compose Multiplatform para la web; el cliente HTTP para conectar la app con la API (Ktor Client, que es el que se usa en Kotlin Multiplatform); el almacenamiento local en Android y en la web; el texto a voz en las dos plataformas; y el envío de correos desde PHP. Para cada uno hay documentación oficial (apartado 3.8), y varios temas los vamos a ver en clase durante el curso.


HARDWARE Y SOFTWARE

- Computadora: portátil con procesador AMD Ryzen 7, 32 GB de RAM, tarjeta gráfica NVIDIA RTX 3070 Ti y Ubuntu. Es suficiente para Android Studio y para el emulador de Android.
- Dispositivos de prueba: un celular Android y un iPhone (para probar la versión web en Safari).
- Software: Android Studio, Visual Studio Code, PHP, MySQL, Git y GitHub. Todo es gratuito.


SERVICIOS EXTERNOS

alwaysdata (servidor y base de datos), Brevo (correos) y GitHub (repositorio del código). Opcionalmente, Google Play para publicar la app.


LIMITACIONES

- La versión web depende de una tecnología en Beta.
- En la web, el curso necesita conexión; el uso sin conexión lo garantizo solo en Android.
- Los planes gratuitos tienen límites (disco, memoria, correos al día). Si el proyecto creciera mucho, habría que pasar a un plan de pago (apartado 3.7).
- La calidad de la voz sintética depende de cada dispositivo.
- No hay versión para iPhone como app instalada, porque para compilarla hace falta una computadora Mac. En un iPhone se puede usar la versión web.


RIESGOS TÉCNICOS

1. La cantidad de contenido. Es el riesgo principal. Cada unidad necesita vocabulario, frases, ejercicios, explicaciones e imágenes, y todo hay que revisarlo. Para reducirlo, limité el alcance a 10 unidades (apartado 3.4), uso una plantilla fija para cada unidad y puedo usar inteligencia artificial para hacer borradores que después reviso yo.
2. La web en Beta. Si algo de Compose Multiplatform no funciona bien en el navegador, la versión de Android no se ve afectada, porque la hago primero. En el peor caso, la web tendría menos funciones que Android.
3. Sincronización. Es fácil equivocarse y perder progreso. Lo reduzco con una regla sencilla (gana el cambio más reciente) y con pruebas específicas.
4. Dependencia de servicios gratuitos. Si alwaysdata o Brevo cambian sus condiciones, la app sigue funcionando sin conexión, y el servidor es PHP estándar, así que se puede mover a otro alojamiento.
5. Tiempo. Lo trato en el siguiente punto.


TIEMPO DISPONIBLE

Tengo desde diciembre de 2026 hasta marzo de 2027, compaginándolo con las clases y con un trabajo en hostelería. Por eso ordené el trabajo para que todo lo imprescindible, en Android y en la web, esté terminado y probado con usuarios antes del 15 de febrero de 2027. Para no llevarme sorpresas al final, el proyecto compila para las dos plataformas desde el primer día. Después de esa fecha solo quedan correcciones pequeñas y la memoria (apartado 3.3). Si me retraso, recorto primero lo deseable (diploma y estadísticas) y no lo imprescindible.


CONCLUSIÓN

Creo que el proyecto es viable. Las tecnologías son las que uso en clase o están muy relacionadas, el hardware y el software que necesito ya los tengo, los servicios externos son gratuitos y el alcance está limitado a lo que puedo hacer en el tiempo disponible. El punto débil es la cantidad de contenido, y por eso el alcance es de 10 unidades y no del curso completo.
